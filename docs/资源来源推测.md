## 1. 地形与地理数据

### 1.1 高程 DEM

**可以确定的部分：**

- `data/terrain.js` 的高程是真实地形，不是随机或手绘数据。
- 解码后是 **400×391 = 156,400 个 `Uint16` 值**，每个值单位是米，解码后约 312.8 KB。
- 高程范围：**0–5953 m**，平均约 **1164 m**。
- 覆盖范围精确为：

| 边界 | 值 |
|---|---|
| 西 | 100.0000°E |
| 东 | 118.0000°E |
| 南 | 23.5000°N |
| 北 | 38.5000°N |

- 这是 Web Mercator 瓦片坐标反推出来的：`zoom = 7`、`x0 = 25486.222…`、`x1 = 27124.622…`，正好对应 100°E–118°E；`y0/y1` 对应 38.5°N–23.5°N。
- `metersPerPx = 1048.309`，正好等于 `156543.03 × cos(31°) / 2^7`。31°N 正是这个范围的中心纬度。这说明高程和底图是沿一套 **XYZ 瓦片管线** 组装的，而不是随意裁一块 GeoTIFF。
- 网格单元约 **4.29 km × 4.29 km**，说明原始 DEM 被大幅降采样，目的是控制 `terrain.js` 的体积。

**高程抽样与真实地形对比：**

| 地点 | 经纬度 | `terrain.js` 高程 | 现实大致高程 | 判断 |
|---|---|---|---|---|
| 瑞金 | 116.02, 25.89 | 225 m | 约 200 m | 合理 |
| 遵义 | 106.93, 27.70 | 900 m | 约 850 m | 合理 |
| 泸定桥 | 102.23, 29.91 | 2258 m | 桥面约 1300 m | 偏高，4 km 网格把峡谷两侧山地平均进来 |
| 夹金山 | 102.68, 30.85 | 3547 m | 垭口约 4114 m | 偏低，网格平均导致 |
| 贡嘎山 | 101.88, 29.60 | 5638 m | 7556 m | 明显被削平，证明经过重采样/平均 |
| 成都 | 104.07, 30.67 | 499 m | 约 500 m | 很准 |
| 松潘草地 | 103.05, 33.00 | 3513 m | 约 3500 m | 很准 |
| 六盘山 | 106.20, 35.60 | 2456 m | 约 2500 m | 合理 |
| 吴起镇 | 108.17, 36.93 | 1384 m | 约 1300 m | 合理 |

**最可能的来源：**

1. **SRTM 90m / 30m**：最常见、最容易获取的全球 DEM；但陡峭地区有空洞，需要填补。
2. **ASTER GDEM**：覆盖全球，和 SRTM 类似。
3. **Copernicus DEM 30m / 90m**：无空洞、质量稳定，适合自动化管线。
4. **GMTED2010**：约 250 m 分辨率，无空洞，适合中小比例尺。
5. **ETOPO1**：约 1.8 km 分辨率，包含海洋；如果构建脚本把海洋裁成 0，也能得到类似结果。
6. **Terrarium / Mapbox Terrain-RGB 等编码 DEM 瓦片**：通过 RGB 解码得到米制高程，再重采样。这是最符合“XYZ 瓦片 + 重采样”痕迹的一类来源。

**不能确定的原因：**

- 整数米的高程值不是数据指纹；上述 DEM 产品在 4 km 网格上通常只差几十米。
- 原始瓦片、构建脚本和下载地址都没有随包发布。
- 没有 `.prj`、`.tif`、XML 元数据或数据版本号。

**结论：** 真实全球 DEM 可以确定；具体是哪一套 DEM 产品，无法从成品反推。若必须押一个，我会优先猜“**通过 Python 瓦片管线下载的 SRTM/Copernicus 类 DEM，重采样到 400×391**”。

### 1.2 地形纹理

**文件特征：**

- 3072×3003 JPEG，base64 内嵌在 `terrain.js`。
- 没有 EXIF、XMP、C2PA、版权字段；只有 JFIF 96 dpi。
- 画面是**土黄/棕色晕渲地形 + 青色河网**，没有地名、没有国界、没有行政区界。
- 右上角有红色印章“碳基出题人”，是作者水印，不是底图署名。

**我做的对比：**

| 候选底图 | 结果 |
|---|---|
| Esri World Terrain Base | 白灰色调 + 黄色道路，明显不符 |
| Esri World Shaded Relief | 浅灰晕渲，明显不符 |
| Esri World Physical Map | 淡黄/淡绿，明显不符 |
| OpenTopoMap | 有地名、有等高线，明显不符 |
| Stamen Terrain Background | 风格最接近（米色底、棕色晕渲、蓝色河网、无标签），但当前公开端点返回 503/401，未能直接取图对比 |

**另一个证据：**

我用 `terrain.js` 的 400×391 DEM 生成了一张晕渲图，与纹理做亮度相关性比较，相关系数约 **-0.11**，基本不相关。两者的大地形轮廓相似，但明暗细节不同。这说明：

- 纹理**不是**直接用这份 400×391 粗 DEM 渲染的；
- 它要么来自更高分辨率的第三方底图，要么来自另一套更高分辨率 DEM；
- 纹理可能经过调色/压缩，颜色对比不能作为唯一依据。

**最可能的来源：**

- **Stamen Terrain Background 一类无标签晕渲底图**（风格最接近）；
- 或 **Mapbox / Esri / 其他 XYZ 底图服务** 的无标签地形样式；
- 或作者用更高分辨率 DEM + 河流矢量自行渲染的晕渲图，再调成暖色调。

**结论：** 可以确定是“无标签晕渲地形底图”，不能确定具体服务商。若二次分发，建议确认底图服务的署名要求。

### 1.3 河流数据

`terrain.js` 里有 5 条 3D 河流：

| 河流 | 点数 | 经度范围 | 纬度范围 |
|---|---|---|---|
| 金沙江·长江 | 1097 | 100.20–117.99 | 25.98–31.10 |
| 大渡河 | 166 | 101.93–103.72 | 29.20–30.80 |
| 乌江 | 270 | 105.52–108.47 | 26.77–29.67 |
| 赤水河 | 118 | 105.21–106.36 | 27.65–28.75 |
| 湘江 | 258 | 110.69–113.14 | 25.65–28.87 |

**关键发现：**

- 底图纹理里有一套**更密集的河网**，是底图自带的。
- 我把这 5 条 3D 河流叠加到纹理上，红色矢量线与底图的青色河网**并不重合**。说明它们是两套独立数据。
- 5 条河都有中文名，折线点很密，不像临时手画的几条线。

**最可能的来源：**

1. **公开矢量河网**：Natural Earth 10m rivers、HydroSHEDS、HydroRIVERS 等，按长征相关区域筛选出 5 条主要河流，再人工命名/合并（例如“金沙江·长江”）。
2. **DEM 自动提取**：用流向/汇流累积提取河道，再人工筛选和命名。`使用说明.md` 写的是“河流由高程数据自动提取”，支持这一可能。
3. **两者混合**：底图河网来自瓦片服务，3D 河流来自矢量数据或 DEM 提取。

**结论：** 5 条 3D 河流是“为讲课服务的主要河流示意”，不是精确水文数据；具体来源无法确定，但“公开矢量河网或 DEM 提取 + 人工筛选”是最合理的解释。

### 1.4 地形部分总结

| 判断 | 置信度 |
|---|---|
| 高程是真实全球 DEM | 确定 |
| 使用 XYZ 瓦片管线（z7 基准、中心 31°N） | 高 |

| 纹理是无标签第三方晕渲底图或自定义渲染 | 中高 |
| 纹理具体服务商是 Stamen/Mapbox/Esri/自定义 | 低 |
| 5 条 3D 河流来自公开矢量数据或 DEM 提取 | 中 |

## 6. 构建与录屏链

这些脚本没有随包发布，只能从代码引用和生成物特征反推。

### 6.1 `build_terrain.py`

证据：

- `data/terrain.js` 第 1 行：`// 由 _build/scripts/build_terrain.py 生成，请勿手改`
- 文件是 Python 在 Windows 上以文本模式写出的（CRLF）。
- 输出包括：base64 `Uint16` 高程、base64 JPEG 纹理、河流折线、Web Mercator 参数。

推测依赖：

- `requests` / `xyzservices` / `mercantile`：下载或拼接 XYZ 瓦片
- `numpy` / `Pillow`：解码、重采样、拼接、导出
- 可能还有 `rasterio` / `elevation` / `srtm` 等 DEM 库

### 6.2 `make_pano.py`

证据：

- `js/vr.js` 注释：全景图由 `_build/scripts/make_pano.py` 转成 `assets/vr/<id>.js`
- `assets/vr/ldq*.js` 第 1 行：`// 由 make_pano.py 生成`
- 输出是 `window.VR_IMG[id] = "data:image/jpeg;base64,..."`

推测：Python + Pillow 读取全景图，base64 编码，写入 JS 文件。目的仍是绕过 `file://` 的图片加载限制。

### 6.3 录屏/演示脚本

## 8. 置信度与局限

### 8.1 可以确定的

- 高程是真实 DEM，覆盖 100°E–118°E、23.5°N–38.5°N，重采样到 400×391。
- 使用 Web Mercator / XYZ 瓦片管线（z7 基准，中心纬度 31°N）。
- 地形纹理是无标签晕渲底图，带后期水印。
- 12 张插画和 3 张全景是 AI 生成（作者注明 + 文件特征）。
- 音效全部由 Web Audio 合成，没有外部音频文件。
- Three.js r147 + OrbitControls 经典版，MIT。
- 字体全部是系统字体，无 Web Font。
- 代码是原生 JS，无框架、无构建、无 npm。

### 8.2 高度可能的

- 地形/底图来自 XYZ 瓦片服务，DEM 和底图可能来自不同 provider。
- 构建链是 Python，脚本由作者或 AI agent 编写。
- 代码主体由 Claude 系模型生成或大幅改写。
- 5 条 3D 河流来自公开矢量河网或 DEM 提取，再人工筛选命名。

### 8.3 仍然未知的

- 具体 DEM 产品（SRTM / ASTER / Copernicus / GMTED / ETOPO / 其他）。
- 具体底图服务商（Stamen / Mapbox / Esri / 自定义）。
- 具体图像模型（即梦 / 可灵 / Midjourney / SD / 其他）。
- 具体代码模型和版本（Claude 3.5 / 3.7 / 4.x，或混合使用多个工具）。
- 史实文字的具体参考资料。
- 背景音乐的原曲来源。

### 8.4 方法上的局限

- 无 EXIF/XMP/C2PA，图像来源只能靠视觉风格和规格推断。
- 无原始瓦片/脚本，DEM 和底图只能靠投影、分辨率、高程统计推断。
- 不同 DEM 在 4 km 网格上差异很小，无法用高程值反推产品。
- 底图可能经过调色/压缩，颜色对比不能作为唯一证据。
- 代码风格可以被模仿，换行符可以被工具改写，AI 来源判断不是密码学证明。
